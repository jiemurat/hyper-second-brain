# Making: deliverables, outlines, reusable pieces, and feedback

This reference holds assembling a deliverable from the vault, the outline of a piece of writing, the pieces of work worth reusing, showing work early and keeping its feedback, and the outline at a project's start. The rules that hold for the whole vault are in `HYPER-SECOND-BRAIN.md`; this file names them and does not repeat them.

## Assembling a deliverable

Use this when the user asks for help producing a deliverable: a report, a presentation, a proposal, a plan, an event. Most components can be found or put together instead of made from nothing.

1. Name the output and break it into the components it needs. For a conference they might be an agenda, a list of sessions, a checklist for the speakers, an announcement, an invitation, and a website.
2. For each component, search the vault (`../hsb-find/SKILL.md`) for earlier versions, models, cut parts of past projects, checklists, notes, and examples the user admires.
3. Give the user the list of components: under each, the candidate notes with their titles and folders, or "to make".
4. When the user asks for a draft, write it as a separate note in the project's folder, put together from those notes: each part links to the note it comes from and keeps that note's source line.

Done when every component names its candidate notes or says "to make", and a draft you wrote links to the notes it comes from.

## The archipelago of ideas

Use this when the user starts a piece of writing (an essay, a talk, a brief, a report) and wants to avoid a blank page, and as the outline offered at a project's start. Write it as a separate note in the project's folder.

1. Select, in exploring mode: gather the sources, ideas, and points that will carry the piece, the user's own notes and thoughts included.
2. Write the note: one entry per source, with a link to the user's full note on it, and under it only the points this piece will use, with the bold and highlight marks they already carry (`hsb-distill`).
3. Set the order in a separate step, in finishing mode: follow the order the user gives, or propose one and wait for the yes.
4. Stop gathering once the material is enough for the piece: the user then writes the bridges between the points.

Selecting and ordering stay apart: selecting is open to every option, ordering works only with what is already on the page.

Done when every selected point stands under its source with a link to the full note, and the order was set in its own step.

## Pieces worth reusing

A reusable piece is a concrete part of the user's work that a later project can build on. Five kinds are worth keeping: distilled notes, parts cut from a project, work in process (documents, graphics, agendas, plans), final deliverables, and material made by others (reused only with their permission).

- When the user finishes or shares such a piece (a post, slides, a diagram, a recording, an answer to a common question, a checklist, a retrospective), offer once to keep it, and place it with `../hsb-place-an-item/SKILL.md` on the yes.
- When the user does a similar piece of work a second time, offer to keep the first result as a piece for the next time.
- Keep each piece's source line, and name every source and influence it borrows from.
- When the user says how much time they have, propose the largest piece of the project that fits that time: a small piece can be finished in any gap.

When a project finishes, `hsb-projects` moves its reusable pieces out with the rest of the material that serves other work.

Done when each piece the user wanted kept sits in its place with its source line, or the user declined the offer.

## Showing early and feedback

A small version is easier to show and to change while there is still time.

- When the user asks for help with a piece of work, suggest once showing a small early version to one person before polishing it; the user chooses the person and sends it.
- When the user brings back feedback, list in the report the changes it suggests: the feedback starts the next round of the work. Keep it as a note in the project's folder, titled by its source and date in the language of the project's notes, with the user's words quoted as said, when the user asks for that or says yes to your offer.

Done when the feedback stands in the project's folder in the user's words, and the user has the list of the changes it suggests.

## At a project's start

Use this when `hsb-projects` starts a project and the user wants an outline of the work, or the project has a deliverable. Plan the project and stop after a short first pass; its work starts when the user asks.

1. Offer the outline that fits the project: an archipelago of ideas for a piece of writing ("The archipelago of ideas"), the goals and the first split of roles for work with others, a packing list and an itinerary for a trip.
2. Write it, on the user's yes, as a note in the project's folder from what the folder and the vault hold.
3. When the project has a deliverable, offer "Assembling a deliverable".

Done when the outline is in the project's folder or the user declined it.
