# Sharing: notes for others, feedback on a draft, working with others

This reference holds preparing a note for readers who lack the user's context, feedback on a draft the user wrote for others, and what goes where when work becomes shared. The rules that hold for the whole vault are in `HYPER-SECOND-BRAIN.md`; this file names them and does not repeat them.

## Contents
- Preparing a note for others
- Feedback on a draft
- Working with others

## Preparing a note for others

Use this when the user wants to share a note or a folder, or people who lack the user's context have to understand it. A personal note is rough because only the user reads it; a note for others has to stand on its own.

1. Learn who will read the note and what they should do with it, and the language they read; ask the user, in one message, what is unclear.
2. Read the note, and the notes it builds on when the readers need their context.
3. Write a new note for these readers:
   - a title that says what it is and for whom;
   - first, a short summary in the form of `../hsb-distill/references/layers.md` → "The summary", so that a reader gets the gist at a glance;
   - then the content: each key term defined, headings where they help (and a short list of contents when the note is long), the background the readers lack, and the reasoning behind each conclusion;
   - when a "Team note form:" line names a form for these readers, that form, and for no other readers: where it sets an opening or an ending, it comes before the summary or after everything else.
4. Leave out what core rule 3 names.
5. Check the note against the five questions of `HYPER-SECOND-BRAIN.md` → "Notes", and fix what fails.
6. Place the note with the steps of `../hsb-place-an-item/SKILL.md`: usually next to the original, in the folder of the work it serves.

Done when a reader with none of the user's context can follow the new note, the original is unchanged, and the user knows where the new note is and what was left out.

## Feedback on a draft

Use this when the user wrote a draft for others and asks what you think before it goes out. Answer in the chat: for each of the five questions of `HYPER-SECOND-BRAIN.md` → "Notes", say yes, or what is missing and where (the heading and the first words of the passage); then name each personal or sensitive detail the readers would see. The draft stays the user's to edit: change nothing, and write a revised version as a new note only when the user asks. Done when the user has the answer to the five questions and the list of the details, and the draft is unchanged.

## Working with others

Use this when other people begin to work with the user on a project, area, or topic.

1. Tell the user what goes where: the shared material (what the group edits and delivers) belongs on the shared platform, in the team's structure, under the exact name the vault folder has now, while the user's own notes about it stay in the vault.
2. List the items of the folder that have become shared, each with its name. The user puts them on the shared platform. When an item's home is there, a note in the vault links to it instead of keeping a second copy; move the vault copy to Archives only on the user's yes.
3. Ask once whether the team keeps a playbook for its shared spaces or a standard form for its notes. When it keeps a playbook, ask where it lives, write the line `- Team playbook: <where it lives>` under "Lasting choices", and follow it for the shared material.
4. When the team has a standard form for its notes, write the line `- Team note form: <the form or where it lives>, for <the team>` under "Lasting choices"; it applies only to notes meant for that team.

Lasting choices are written as `HYPER-SECOND-BRAIN.md` → "What you may do and what you ask first" says.

Done when the user knows which material goes to the shared platform and under which name, nothing moved without a yes, and the team's playbook and note form are recorded when the team has them.
