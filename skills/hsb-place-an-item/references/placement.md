# Placing an item: the rules of choosing the place

This reference holds the rules that belong to placing an item. The rules that hold for the whole vault are in `HYPER-SECOND-BRAIN.md`; this file names them and does not repeat them.

## The order

For each item, in this order:
1. Decide when the item will be relevant next, and name the nearest action it serves. Use the user's current projects from step 1 of SKILL.md.
2. Choose the category with the tests in `HYPER-SECOND-BRAIN.md` → "Categories".
   - An item that serves a current project goes in that project's folder, even when an area or resource folder would also fit. A project's folder holds what its goal needs: material that is only interesting goes to a Resources folder.
   - An item that serves several projects goes in the folder of the one higher on the Project List, with a link to it from the others (see "One item, one place").
   - Otherwise take the most actionable category that fits.
   - When you cannot tell a project from an area, or an area from a resource, apply the next two sections.
3. Choose the folder: the specific project, area, or resource the item serves (see "Choosing the folder").
4. When another platform suits the item's kind, place it in the vault all the same and put a reminder on the list for the report (see "Other platforms").
5. Check that the item will live in one folder, that the folder belongs to what the item serves, and that you can state the reason in one sentence. When you cannot, treat the item as a doubt (see "Doubts and sensitive items").

Example: an article on typography that the user needs for the brochure project goes in the brochure project's folder. The same article, saved with no current use, goes in a Resources folder named `typography`.

Done when every item has a category, a folder, and a reason in one sentence, or is marked as a doubt or a question.

## Telling projects from areas

Projects end and areas continue; the tests in "Categories" decide.
- An effort with a goal and a timeframe is a project. An effort with no end is an area. Hiring, events, strategic planning, vacations, and professional development look like projects but are areas; each one yields projects (a particular hire, a particular event). An effort someone else carries out for the user is still a project: the user keeps its quotes, contracts, and budget.
- An effort with only a goal or only a timeframe is a project in the making. Place the item in the area the effort falls under (in the Inbox when no area fits), say in the report that the effort lacks a goal or a timeframe, and create no project folder.
- A project usually falls under an area (running a marathon falls under Health). Name the area when the user confirms a new project.

## Telling areas from resources

The topic never decides the category; the user's relationship to it does.
- Test whether something the user is responsible for would suffer if they stopped attending to the topic, with no one else to take it up. If so, the topic is an area. When the user is exploring, learning, or curious, with no duty attached, it is a resource.
- The same topic can be either: nutrition research is an area for a public health professor and a resource for a student of another field.
- When the item serves a responsibility that already has an area folder, it goes there. When the user's relationship to the topic is unknown and the item would need a new area, ask, and leave the item in the Inbox until the answer.
- Keep personal and sensitive details (health, finances, family) out of resource folders, so that a resource note or folder can be shared without combing through it. Put such details in the relevant area.

## Choosing the folder

- Read the `_about.md` of an existing folder you are considering (`HYPER-SECOND-BRAIN.md` → "Folder about files"): its "Belongs here" and "Not here" lines settle close calls.
- Put the item in the folder of the specific project, area, or resource it serves, never loose in a category folder. A project folder belongs in the Projects folder, an area folder in the Areas folder, a resource folder in the Resources folder. Besides an `_about.md`, the Project List is the one note that sits directly in the Projects folder.
- When that folder does not exist, create it as `HYPER-SECOND-BRAIN.md` → "What you may do and what you ask first" allows. A new project folder needs a goal and a timeframe: ask the user for the missing part.
- Name the folder for the one outcome of the project (for an event, the name the user calls it), for the responsibility, or for the topic, following `HYPER-SECOND-BRAIN.md` → "Folders and names".
- A project or an area that you infer from the text of an item counts as one the user has not mentioned: ask before you create its folder.
- An item of something inactive goes to the archive folder of that project, area, or resource, named as it was; create the archive folder when it is missing.
- Put a new item beside the material it may connect to and leave a rough note as it is written: no critique, trimming, or tidying.
- When a category folder that `project.md` names does not exist, tell the user, offer `hsb-doctor`, and place nothing there.

## One item, one place

An item lives in one place: two versions leave the user unsure which is current. Prefer moving, and link when the original must stay.
1. Move one item when only it serves the new place.
2. Move a folder when the whole group serves it.
3. Link to the item from the new place when other work still needs the original where it is. Write the link in a note inside the destination folder; when the folder has no suitable note, create a short one titled for the item.
4. Tag the items with one shared tag when the vault already relies on tags and you want to relate many items without moving them.

When you find the same item in two places, tell the user both paths, ask which one is current, and keep both until the answer.

## Other platforms

The vault holds every item the user hands over or asks to keep: route nothing to another app. Some kinds of items are usually kept better on another platform; place such an item in the vault like any other item and remind the user which platform suits it:
1. A secret (a password, card details, an access key) or a sensitive record (a tax or government document, health records and results): an encrypted password manager.
2. An appointment or a meeting at a specific time: a calendar.
3. A task the user can do at any time: a to-do list app, under the project it serves or, when it serves no project, under the area it serves. A note that holds tasks among its text (the action items or decisions of meeting minutes) stays whole.
4. A document the user edits together with other people: a cloud storage drive.
5. A file too large or too specialized for the vault: the computer's file system.

For each such item:
- Place it by "The order": the folder of the project, area, or resource it serves; create that folder when none fits, as `HYPER-SECOND-BRAIN.md` → "What you may do and what you ask first" allows. An item the user only said (a task, an appointment, a secret) becomes a short note there in the user's words, with its date and time when it has them; when the folder already has a note for such items (a task list, a list of dates), add the item to it; when a note this request writes already holds the item (a "Where I left off" entry), that note is its place: write no other.
- Put one reminder line per item on the list for the report: the platform that suits it and the note that holds the item.
- Give no reminder when "Lasting choices" says the user keeps that kind of item in the vault or does not use that platform. Record such a choice there when the user states it.

Example report lines:
- A calendar suits it: dentist check-up, 14 October, 15:00, saved in `2. AREAS/Health/Dentist check-up.md`.
- A to-do list app suits it, under PLAN THE OFFSITE: book the venue by 20 October, added to `1. PROJECTS/PLAN THE OFFSITE/Tasks.md`.
- A password manager suits it: the router password, saved in `2. AREAS/Home/Router login.md`; nothing quoted.

## Doubts and sensitive items

Placement is forgiving: the user finds most things by search and items can move later, so a quick reasonable placement beats an unanswered question.
- When the tests do not settle the place, put the item in the most actionable plausible category and report it as `doubt:` with the alternatives you weighed.
- Ask instead, and leave the item in the Inbox until the answer, when the item is a sensitive record or when placing it would create a commitment (a new project or area). An answer of "not now" or "later" keeps the item in the Inbox. A sensitive record holds private personal data of the kinds the user named: health records and results, tax and government documents, identity documents, bank and card statements, and notes about relationships. An ordinary bill, an appointment, or a note on a health or money topic is not one.
- When "Lasting choices" in `project.md` already says where that kind of item goes, put the item there without asking.
- When you ask about a sensitive record, offer the choices: a named area folder (and say that an encrypted password manager suits such records), or the Inbox for now. Offer to remember the answer as a lasting choice.
- A note that holds a secret (a password, card details, an access key) is not a sensitive record to ask about: place it by its use, tell the user which note holds the secret, quote nothing, and suggest the password manager (see `HYPER-SECOND-BRAIN.md` → "Data and secrets").

## The report

Write the report in the user's language, in the chat, as plain lines:
- One line per item: its name as it is, the folder it went to, and the reason in one clause. Name every folder you created, and every project folder that entered or left Projects, spelled exactly as in the vault.
- The items that wait for an answer, each with its question and choices. Put all questions together at the end.
- The doubts: `doubt:` and the alternatives.
- The reminders of other platforms, one line per item.
- The `_about.md` files you created or updated, each with one clause for the reason.
- The lasting choices you recorded.

Done when the user can see where every item went, why, and what you need from them.
