# The life of a project: start, change, finish, reopen

This reference holds the rules of a project's life. The rules that hold for the whole vault are in `HYPER-SECOND-BRAIN.md`, and the rules of placing an item in `../hsb-place-an-item/references/placement.md`; this file names them and does not repeat them.

## Contents

- Starting a project
- Changing a project
- Shrinking the scope
- Finishing a project
- Reopening a project

## Projects from efforts

Use this when the user lists projects or efforts, when an item filed as a project fails the test of a project, and when an area has work underway but no project folder. Splitting an area into its projects shows the user how much they have committed to, and ties each effort to an outcome that can be reached.

1. Test each effort as `placement.md` → "Telling projects from areas" says. An effort with no end goes to Areas; an effort that lacks its goal, its timeframe, or both is a project in the making: ask for what is missing.
2. For each area with work underway, find the concrete efforts in it from the user's words, the area's notes, and the folders in Projects. Take only efforts the user has underway or has committed to.
3. Name each effort for the one outcome it delivers, one project per outcome: each hire, each event, each report, not one project for a run of similar work. When an effort is too large to finish in the foreseeable future, take its next finishable piece as the project. Draft a goal (the outcome that marks it done, such as finalized, approved, launched, or published), a timeframe (a date or a period; a rough one is enough), and the area it falls under, or none.
4. Put the projects to the user with their names, goals, and timeframes, together with your other questions.
5. Start each confirmed project ("Starting a project"), then show the user the confirmed projects grouped by area, so that the load of each area is visible.

Done when every effort the user called a project is a confirmed project, an area, or a project in the making with its question kept, and every confirmed project has a folder and an entry.

## Starting a project

Use this when the user confirms a project or starts one.

1. Take the confirmed goal and timeframe, or ask for the missing part. When the user says the effort has no end, it is an area: place its material as `hsb-place-an-item` does.
2. When the list already holds about twenty projects or more, tell the user how many it holds and which sit at the top, and ask whether the new project joins them, replaces one, or waits.
3. Create the project folder in Projects, named as `HYPER-SECOND-BRAIN.md` → "Folders and names" says, and add the project to the list as "Project List" says; when there is no list yet, create it with this first entry.
4. Ask the user what they already know about the project, what they still need to find out, what their goal or intention is, who could give them insight, and what they could read or listen to. Write the answers, in the user's words, into the project's first note in its folder; when the user skips the questions, write no note. This is a first pass: keep it short, because the material may never be needed again. When the user wants an outline of the work, or the project has a deliverable, offer it as `../hsb-create/references/making.md` → "At a project's start" says.
5. Work back from the goal: name what the project needs to reach it (information, contacts, plans, reusable material), and search for it in the project's area first, then in Archives, then in Resources. Move into the project folder what serves this project alone, and link to what other work still needs (`placement.md` → "One item, one place"). Moving about 20 items or more needs the user's yes (`HYPER-SECOND-BRAIN.md` → "What you may do and what you ask first").

Done when the project has its folder and its entry with a goal and a timeframe, the first note holds the user's answers or the user skipped them, and the report says what the search brought in and from where, or that it found nothing.

## Changing a project

Apply these when the user's words show the need, and change the entry in the same step:
- Rename the project when its scope or direction changed; repair the links (`HYPER-SECOND-BRAIN.md` → "Links") and tell the user the new name, so that they can use it on their other platforms.
- Split it when it grew too large to finish in the foreseeable future: propose the smaller projects ("Projects from efforts") and create them once the user confirms.
- Shrink its scope ("Shrinking the scope"), finish it ("Finishing a project"), or reopen it ("Reopening a project").

Done when the folders and the list show the change the user asked for.

## Shrinking the scope

Use this when a project grows past the time and attention the user has, or when the user keeps putting it off. A smaller version that ships brings what the project was for sooner than a whole one that waits.

1. List the parts of the project and the user's constraints: budget, deadline, and the time available. Ask for any that is missing.
2. Mark the parts to drop, reduce, or postpone first: the hardest or most expensive, the most uncertain or risky, and those that matter least to the goal.
3. Put the marked parts to the user. Save the parts the user cuts in a note in the project folder for ideas kept for later, and tell the user that nothing is lost: a cut part can come back in a later version or serve another project.
4. Name the smaller version that keeps most of the value, such as a series of articles instead of a book, or a sketch instead of a full design. When the goal or the timeframe changes, change the entry.

Done when the user has confirmed a smaller version, the cut parts are saved, and the goal and the timeframe of the entry describe that version.

## Finishing a project

Use this when the user says that a project is finished, paused, cancelled, or handed over.

1. Ask whether anything is left to wrap up: final approvals, paperwork, sending the deliverables. Go on when nothing is, or when the user says to archive it anyway.
2. Offer a short look back: did the project reach its goal and why, what worked and could be repeated, what went wrong and would change next time. Write the answers, in the user's words, into a note in the project folder before it moves; the next similar project finds it there.
3. Look through the folder for material that serves other work: brainstorms, background research, slides, interview notes, frameworks, parts cut from the work, work in process, and the final deliverables. Place each such item by the rules of `hsb-place-an-item`; a new Resources folder for its topic needs no question.
4. When the project's result has to be kept up after it ends (a weight, a clear inbox, a balanced budget), check that an area holds the habits that keep it; when none does, propose one.
5. When the project is paused, cancelled, or handed over, offer its final "Where I left off" entry as `../hsb-create/references/focus.md` → "When a project stops" says. Move the folder to Archives with its name unchanged, and repair the links (`HYPER-SECOND-BRAIN.md` → "Links").
6. Remove the project from the list.

Done when every item of the folder has moved out or stays on purpose, the folder sits in Archives under its name, the list no longer names it, and the report names the project as finished, paused, cancelled, or handed over, with what moved out and where.

## Reopening a project

Use this when a project in Archives becomes active again. Move its folder back to Projects, named as `HYPER-SECOND-BRAIN.md` → "Folders and names" says for a project, and add it to the list; ask the user for a new goal and timeframe when the old ones have passed. Repair the links and tell the user.

Done when the folder sits in Projects under a project name, and the list names it with a goal and a timeframe.
