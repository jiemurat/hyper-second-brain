# The Project List: building and reviewing it

This reference holds the rules of building and reviewing the Project List. Its form, its language, and when an entry changes are in `HYPER-SECOND-BRAIN.md` → "Project List"; this file names them and does not repeat them.

## Contents
- What the list is for
- Building the list
- Reviewing the list

## What the list is for

The list holds every outcome the user is committed to now, each with a timeframe, in one note, so that the user sees the whole load at once and can say yes or no to a new commitment on purpose. A task list says what to do next and a wish list says what might be nice; the Project List says what the user has promised to finish. A list of ten to twenty projects is common.

## Building the list

Use this when there is no list and the user asks for one or names a first project, when the user asks for a fresh inventory of their commitments, and when a review finds the list stale. A list that exists moves first into the Archives folder, in a folder named `Project List YYYY-MM-DD` with today's date, and its entries become candidates.

1. Ask the user, in one message, for a quick first pass of whatever comes to mind, work and personal alike; rough answers are enough:
   - what worries them right now;
   - which problem takes more of their attention than it deserves;
   - what needs to happen and is not moving;
   - what they already do that is part of a larger effort they have not named;
   - what they would like to learn, build, express, start, or explore, and which skills or hobbies they would like to take up;
   - what would move their career forward or make life more fun.
2. Add the candidates the vault shows: the folders in Projects, the areas with work underway, and the entries of an archived list. A folder in Projects that the user calls no project (a container or an umbrella that holds a folder per project) stays off the list: record it under "Lasting choices" in `project.md` as ``- Not projects: `NAME` `` (more names comma-separated on the same line), so that `hsb-doctor` and `hsb-re-organize` stop reporting it; a folder that line already names is no candidate. Ask the user to glance at the places where unnamed projects hide (the calendar, the to-do list, the desktop and downloads folders, bookmarks, emails, open browser tabs) and to name what they keep around because it belongs to a larger effort.
3. Run every candidate through `lifecycle.md` → "Projects from efforts". With the confirmation it asks for, ask which projects should take the most attention in the coming week and which little or none, and rank the list that way; rank only the coming week.
4. Write the list as `HYPER-SECOND-BRAIN.md` → "Project List" says, one entry per confirmed project, in the order of step 3.

Done when every project the user confirmed appears once with a goal, a timeframe, an area (or none), and a folder, the list is in priority order for the coming week, and every candidate the user still wants as a project but without a goal or a timeframe is kept as an open question.

## Reviewing the list

Use this when the user asks for a review, and when the user says they feel overwhelmed or stretched thin. A review that ends in cancelling, postponing, or shrinking projects has done its job.

1. Show the user the list in its current order, with the goal, the timeframe, and the area of each project. Point out the projects that look finished, that changed their scope, and that are overdue. In the list itself, write "overdue", in the language of the list and in brackets, after a timeframe that has passed, and remove it when the user sets a new one; a timeframe too rough to compare with today becomes a question for this review. When more than half of the entries are overdue or look finished, the list has gone stale: offer to build it again ("Building the list") instead of going through it entry by entry. A folder in Projects that the user calls no project (a container or an umbrella) stays off the list: record it on the ``- Not projects: `NAME` `` line, as "Building the list" says.
2. Ask the user, in one message:
   - which projects have finished, been paused, cancelled, or handed over, changed their scope, or grown too large;
   - which projects should take the most attention in the coming week, and which little or none;
   - which projects could be cancelled, postponed, made smaller, delegated, or made clearer.
3. Apply the answers with `lifecycle.md`, and rank the list for the coming week: the aim is steady progress on a handful of projects near the top.
4. When the user feels overwhelmed or asks for a full review, also ask which goals they call important that have no project (dreams), and which efforts take their time without a goal (hobbies); both are legitimate and stay off the list. When "Lasting choices" in `project.md` names the user's goals note, write each dream the user names into its dreams section, in the user's words. For a dream, search the vault for what it already holds on the subject, show the user what you found, and offer to make a project of its next finishable piece (`lifecycle.md` → "Projects from efforts"). For an effort without a goal, ask whether it needs one (then it is a project) or is for fun (then its folder belongs in Resources, moved and renamed only on the user's yes). Then offer help with the top project, one at a time (`../hsb-create/references/focus.md` → "One project at a time").

Done when the user has been asked about every project on the list, the answers are applied, and the list is in priority order for the coming week.
